# Thread Ripper 分片并行

[功能目录](README.md) · [项目首页](../../README.md)

### 接管条件

分片引擎接管已登记媒体文件的异步 GET XHR，响应类型须为 `arraybuffer`，没有请求体、URL 用户名／密码或 `withCredentials`。请求头只允许 Range 与 Accept，Range 必须是单一且有明确起止位置的字节范围，例如 `bytes=0-1048575`。

多范围、开放末端范围、未登记文件、超过 64 MiB 的范围和其他不符合条件的请求不进行分片。严格限定接管条件，是为了能完整重建播放器期待的二进制响应，不把无法确定边界的数据拼接起来。fetch 路径参与策略路由，但当前不进行 Thread Ripper 分片接管。

## 分片与调度

播放器请求一个字节范围后，引擎根据近期吞吐、首字节等待时间、候选 Host 数量与并发预算决定片数。预计传输时间很短的请求保留单片，减少额外请求开销；较长请求按目标片大小拆分。目标片大小在 192 KiB 至 4 MiB 之间调整，最终片数还受最大片数和可承担下载的 Host 数限制。

各片覆盖同一个文件范围内互不遗漏的连续区间。例如对 `bytes=0-1048575` 使用四片时，可分别请求四段 256 KiB 数据，再按原始偏移写入同一个缓冲区。实际分片数不固定，也不保证每次请求都会使用多个节点。

节点模型按 Host 与视频记录首字节等待、吞吐和数据块间隔。未测量节点通过探索请求积累数据，不直接当作最快节点；已有测量时，主要片段倾向于交给预计完成时间接近最快节点的来源。模型还考虑同 Host 的并发负载，因为多个请求可能共享一条 HTTP/2 连接，增加请求数不一定增加总带宽。

## 竞速、救援与尾部转移

小范围请求可同时在多个候选节点竞速；某个请求迟迟没有首字节或收到数据后停滞时，引擎可在其他节点补发救援请求。领先请求继续交付后，落后的副本会被取消，以减少重复流量；对未测量节点保留必要样本，避免节点永远没有被测量的机会。

取消尚未收到首字节的救援请求时，除了领先者已收到至少 64 KiB，还要求领先者在救援启动之后继续收到过数据。这样可以区分“正在前进的领先者”和“虽然历史上领先、目前已经卡住的请求”，防止把仍可能有效的救援过早取消。

有空闲并发且没有等待任务时，预计最慢片段尚未下载的尾部可转移给另一节点。拆分点综合原请求速度、另一节点首包等待和吞吐估计，使两部分尽量同时完成；尾部转移也受最大片数限制。

从空闲恢复时，引擎重置网络静默计时，避免把没有下载任务的空闲时长算成网络断连。

## 校验与合并

分片响应必须满足以下条件才会被采用：

- HTTP 状态为 `206`，可读取并解析 `Content-Range`。
- 返回的起止位置与当前片段实际请求范围一致。
- 文件总长度在各响应都提供已知值时保持一致。
- 流中提供了完成该片所需的数据；截断数据不能当作完整片段。
- 竞速请求在同一偏移交付的重叠字节一致。
- 重定向最终地址符合当前 CDN 选择与 PCDN 策略。

返回 `200` 可能意味着节点忽略 Range；直接把整个文件当成片段拼接会破坏偏移。缺少 `Content-Range` 时也无法确认数据属于哪一段，因此这两种情况均不用于分片合并。文件总长度或重叠内容不一致意味着节点可能提供了不同版本的数据，不能单凭响应成功就混合使用。

校验后的数据按偏移写入缓冲区。全部片段完成后，通过合成 XHR 返回播放器请求的范围，并提供相应状态、响应头、进度及完成事件；页面取消、超时或重新打开 XHR 时，相应下载也会停止。

## 初始化段与索引

DASH 的初始化段和索引决定了解码器能否开始播放。引擎可将同一文件开头的初始化段与索引合并获取并缓存，后续请求命中时只返回所需子范围，避免重复下载。

“预热初始化段与索引”控制提前获取可能切换到的表示：同类音视频，视频还要求编码族一致。后台预热使用较低优先级，并为前台工作预留并发，最多保留 64 个头部缓存条目。关闭预热后，不再主动预取其他表示；当前请求触发的头部合并与缓存仍存在。

## 失败与回退

节点错误按类型处理：范围错误、文件缺失等可排除该 Host 对该文件的候选；拒绝访问、限流与网络故障可触发相应排除或冷却。冷却用于避免立即反复请求已经失败的节点，并不把一次连接中断永久认定为节点不可用。

单片达到失败尝试上限或整个任务持续 8 秒没有进展时，本次合成 XHR 失败，由播放器发起后续重试。同一文件同一范围在 30 秒内不再分片；一分钟内三个前台任务失败，会暂停分片 30 秒。发现重叠数据不一致后，当前引擎停止接管后续请求，直至引擎重建。

回退是退出分片调度，CDN 与 PCDN 策略仍然有效。符合策略处理条件的媒体 XHR 仍可能由原生 fetch 完成并通过合成 XHR 返回，而不一定直接调用浏览器原始 XHR。此设计保证策略不会随着下载方式变化而被静默绕过。

## 并行设置

| 设置 | 默认 | 范围 | 含义 |
| --- | --- | --- | --- |
| 下载总并发 | 16 | 3–32 | 同一个引擎内进行中的分片请求总上限，含竞速和预热 |
| 单节点下载并发 | 4 | 1–6 | 单 Host 的请求上限，不超过下载总并发 |
| 每次请求最大片数 | 16 | 1–16 | 初始拆片与后续尾部拆分的上限 |
| 预热初始化段与索引 | 开启 | 开／关 | 是否提前获取可能切换到的表示的头部数据 |

总并发下限为 3，是因为后台预热需要为前台任务保留两个槽位。单 Host 上限限制集中请求压力；总并发、Host 并发和片数限制分别约束不同层次，不能把片数直接视为网络请求数，竞速会为同一片产生额外请求。

并行能利用不同请求或不同 CDN 的可用吞吐，但收益依赖网络、缓存和节点限速方式；竞速、救援和预热也会增加一部分带宽与流量消耗，因此分片并行默认关闭。
